# 第 1 章 内核可编程性的漫长求索

> 本章不出现任何 API。我们只做一件事：沿着"我想在内核里干点事"
> 这个古老的需求，把 eBPF 诞生之前的全部挣扎、它的横空出世、以及
> 之后十年的演进讲成一个连贯的故事。理解了这个故事，后面所有机制
> 都是"理所当然"。

## 1.1 从一个真实需求说起：这件事为什么这么难

把时钟拨回你接到的一个运维工单：

> "线上那台 8 核机器带宽跑满了。netstat 看不到异常连接，
> top 里也没有可疑进程。找出是谁在疯狂发包。"

你手里有四条传统路，我们逐条走一遍，看它们各自死在哪里。

**路线一：iptables/nftables。** 在 OUTPUT 链加 LOG 规则，能记下
每个出向包的五元组。但你翻遍日志也找不到答案——**包经过网络栈时，
内核知道它属于哪个 socket；但 iptables 的规则体系里没有"进程"这个
维度**。你拿到的是一亿条 `DST=1.2.3.4 DPT=443`，而工单要的是
"哪个进程"。

**路线二：改内核源码。** 在 IP 输出路径加几行 printk 把
`current->comm` 打出来？技术上完全可行。但发版周期以年计、你要
维护自己的内核分支、上线一次要重启整批机器——为了排一个工单，
这个代价荒谬到不会有人认真考虑。

**路线三：内核模块（LKM）。** 终于像样了：写一个模块挂
`inet_sendmsg` 的探针，几行代码就能拿到"进程名 + 字节数"：

```c
// 一个"能解决问题"的内核模块（示意）
static int trace_sendmsg(void *p1, void *p2, size_t len) {
    printk("%s sent %zu bytes\n", current->comm, len);
    return 0;
}
```

但它有两个致命属性：

```
  内核模块的风险模型
  ┌───────────────────────────────────────────────────┐
  │  你的 C 代码    ──直接运行于──▶   内核地址空间      │
  │      │                                            │
  │      ├─ 一个空指针解引用  →  kernel panic → 整机宕机│
  │      ├─ 一个野指针写      →  静默数据损坏          │
  │      └─ 每个 Linux 版本 ABI 不同 → 每台机器都要    │
  │         对应内核头重新编译，分发噩梦                │
  └───────────────────────────────────────────────────┘
```

生产环境上一个 bug 的期望损失，足以否决这条路线。

**路线四：用户态旁路。** 轮询 `/proc/<pid>/net/dev`、用 tcpdump
抓包再关联？粒度对不上（tcpdump 无进程维度）、采样开销大、
答案永远慢半拍。

四条路走完，需求本身没有变，但它暴露了内核的一个结构性空白：

```
                 能力 vs 安全：内核扩展方案的空白地带
   高 ┌─────────────────────────────────────────────┐
   能 │                                             │
   力 │          LKM ┌────────┐                     │
      │             │危险区  │      ← 这里是一片空白：
      │   改内核源码│        │        "又安全又可编程"
      │   (重)      │        │        的机制不存在
      │             └────────┘                     │
   中 │      iptables/nft(受限DSL)                  │
      │      /proc、tcpdump(旁观)                   │
   低 │                                             │
      └─────────────────────────────────────────────┘
         低 ──────── 安全性/可控性 ────────▶ 高
```

**eBPF 填的正是这块空白**：接近 LKM 的能力，但把"会不会出事"的
问题从运行时（崩了才知道）提前到了加载时（加载前就证明不会出事）。
这个"证明"由谁做？——验证器。它是整个 eBPF 大厦的地基，也是
第 3 章的主角。在此之前，我们先把历史线补全。

## 1.2 cBPF 前世：1992 年的论文与 tcpdump

eBPF 的"B"是 Berkeley，故事要从 1992 年讲起。

那年，Lawrence Berkeley 实验室的 Steven McCanne 和 Van Jacobson
发表了《The BSD Packet Filter: A New Architecture for User-Level
Packet Capture》。他们要解决的问题是：**抓包工具（当时的 tcpdump
前身）如何在内核里过滤包，才能让拷贝到用户态的数据最少？**

### 1.2.1 论文的核心设计

作者观察到，当时的内核过滤方案（CSPF）把过滤逻辑写死在内核里，
每改一个过滤表达式都要改内核。他们的答案是：设计一个**极小的
虚拟机**，让用户态把"过滤逻辑"编译成这个虚拟机的字节码，注入
内核解释执行——内核从此只负责"安全地跑字节码"，不关心语义：

```
  cBPF 的架构（1992）
  ┌──────────┐  编译   ┌──────────┐  注入   ┌────────────────┐
  │ tcpdump  │──────▶ │ cBPF字节码│──────▶ │ 内核解释器       │
  │ 过滤表达式 │        │ (载荷无关)│        │ 逐包执行、返回   │
  └──────────┘        └──────────┘        │ keep / drop     │
                                          └───────┬────────┘
                                                  │ 只拷贝命中的包
                                                  ▼
                                          ┌────────────────┐
                                          │ 用户态 tcpdump   │
                                          └────────────────┘
```

这个虚拟机小到什么程度？**32 位机、两个寄存器**（累加器 A、变址
X）、固定的指令集（加载/运算/跳转/返回）、没有函数调用、**返回值
只有"保留前 n 个字节"**。过滤表达式（如 `tcp port 22`）由 libpcap
编译成这十几条指令，在内核逐包跑完返回 0 或 n。

### 1.2.2 为什么这个设计赢了

论文著名的贡献是比较实验：同样的过滤任务，新架构在多数真实负载下
比旧方案快 3 倍以上（跳转表解释器 + 少拷贝）。更深远的是它确立的
**架构思想**，二十年后原封不动地被 eBPF 继承：

1. 用户态编译、内核态执行；
2. 字节码是**能力受限的 DSL**，而不是任意机器码；
3. "内核执行陌生代码"的安全前提 = 指令集足够简单、可完全模拟。

### 1.2.3 cBPF 的安全化应用：seccomp

2005 年（Linux 2.6.12），内核把 cBPF 用到了第二个场景：seccomp
（secure computing mode）——进程可以自愿放弃部分系统调用能力，
方法就是提交一段 cBPF 程序过滤自己的 syscall 编号。这证明了
"BPF 字节码"作为**安全边界**的价值：连沙箱都敢把安全托付给它，
因为它的表达能力被阉割到"作不了恶"。

### 1.2.4 cBPF 的天花板

到 2013 年，cBPF 的局限已经写在了墙上：

| 局限 | 后果 |
|---|---|
| 32 位、两个寄存器 | 复杂逻辑写不出来（编译器都难优化） |
| 无函数调用 | 只能平铺直叙 |
| **无数据结构** | 程序算出的结果没地方放——只能返回一个字 |
| 只能过滤 | 无法修改包、无法调用内核功能 |
| 解释执行为主 | 性能天花板低 |

注意第三条：**"算出结果没地方放"**——这正是后来 map 概念的起源
（第 4 章的主角）。历史脉络在此埋下第一颗种子。

## 1.3 eBPF 诞生：用"可证明安全"敲开内核大门

### 1.3.1 提案与争议

2013 年，来自 PLUMgrid 的 Alexei Starovoitov（与 Daniel Borkmann
合作）向内核社区提交了一个激进的重写：把 cBPF 虚拟机推倒重来，
变成 **64 位、11 寄存器、支持函数调用**的通用虚拟机，取名 eBPF。

可以想象内核邮件列表上的第一反应：*"你想让内核跑任意字节码？
疯了？"* eBPF 能进主线，靠的不是性能数据，而是一个**安全论证**：

> 新虚拟机配一个**验证器**。程序加载时，验证器对每条可能的执行
> 路径做符号执行，检查每条指令的状态。只要有一条路径可能越界读、
> 读未初始化数据、跳到非法地址——**拒绝加载**。只有验证器证明
> "这个程序无论输入如何都安全终止"之后，代码才被允许进入内核。

```
  LKM 与 eBPF 安全模型的根本差异

  LKM：                                     eBPF：
  ┌────────┐                               ┌────────┐
  │你的代码 │──链接进内核──▶ 直接执行        │你的代码 │──提交──▶ ┌────────┐
  └────────┘                               └────────┘          │ 验证器  │
       │                                                       │ 符号执行│
       │ 出事在运行时：                                            │ 证明安全│
       ▼                                                       └───┬────┘
  ┌────────┐      ┌────────┐                          通过        │ 拒绝
  │ kernel │◀────│ panic  │                           ▼           ▼
  └────────┘      └────────┘                    JIT编译执行    退出+日志
                                              （运行时无需再担心）
```

一句话：**LKM 的安全责任在你（运行时爆炸），eBPF 的安全责任在
加载时（要么证明安全，要么不许进来）**。

### 1.3.2 落地：3.18 与最初的三件套

2014 年 12 月，Linux 3.18 合入 eBPF 核心。那时的全部家当是：

- 一个验证器 + 解释器（后来才是 JIT）；
- **两种 map**（ARRAY/HASH）——补上 cBPF "结果没地方放"的天花板；
- 一种程序类型 SOCKET_FILTER——沿用 cBPF 的老阵地。

后续十年的所有故事，都是围绕"**增加新的程序类型（新钩子）× 新的
map 类型（新数据结构）× 新的 helper（新内核能力）**"这三条轴线展开
的。记住这三条轴线，下面的发展史就不再是流水账，而是一棵清晰的树。

## 1.4 十年演进一瞥

先上全景时间线，再分阶段讲故事。

```
 1992 ─── cBPF 论文（BSD 包过滤器）
   │
 2005 ─── seccomp：cBPF 首次承担安全职责
   │
 2014.12 ─ eBPF 进主线（3.18）：验证器 + ARRAY/HASH + SOCKET_FILTER ★地基
   │
 2015 ─── kprobe/tc 程序类型（4.1）── tracing 与tc起飞；BCC 诞生
   │
 2016 ─── XDP（4.8）+ 驱动生态（4.8-4.12）；clsact（4.5）；sockmap（4.14）
   │
 2015-2019 ─ BCC 黄金期与痛点：每台目标机都要现场编译（内核头依赖）
   │
 2019 ─── libbpf 时代开启：全局变量(5.1)/100万指令(5.2)/有界循环(5.3)
   │                    ★内核自带 BTF（5.4）→ CO-RE：一次编译到处运行
   │
 2020 ─── fentry/fexit + trampoline（5.5）；struct_ops（5.6）
   │      BPF link + LSM（5.7）；ringbuf + CAP_BPF（5.8）
   │
 2020-22 ─ sleepable(5.10)/memcg(5.11)/timer(5.15)/multi-kprobe(5.18)
   │
 2023-24 ─ tcx（6.6）/netkit(6.7)/user-ringbuf·arena（6.8+）
   ▼
 今天：网络（Cilium/Katran）· 观测（bpftrace/Parca）· 安全（Falco/Tetragon）
```

### 阶段一：网络与 tracing 的起飞（4.1-4.19，2015-2017）

eBPF 有了地基之后，第一个问题就是"还能挂在哪"。4.1 一次性开出
两个重磅钩子：**kprobe**（任意内核函数进出）和 **tc**（流量分类器）。
前者让 tracing 社区疯狂涌入——BCC（2015，IO Visor 项目）把
"写 Python 胶水 + C 片段 + 现场编译"封装成工具箱，`execsnoop`、
`opensnoop` 一夜之间成了排障标配。

2016 年的 **XDP（4.8）** 则把网络能力推到极限：程序挂在**网卡驱动
收包的第一站**，此时连 skb（内核的包描述结构）都还没分配——
丢包成本降到理论最低。Cloudflare 很快公开了用 XDP 扛 DDoS 的实践
（后来的 Katran 则是 Facebook 的四层负载均衡器）。同一时期，
clsact（4.5）让 tc 双向挂钩标准化，sockmap/devmap（4.14）铺开
"用 BPF 做转发"的路线。

### 阶段二：BCC 的痛点与"一次编译"革命（2015-2019）

BCC 越流行，它的结构性缺陷越刺眼：程序在**目标机器上现场编译**，
于是每台机器都要装内核头文件和 LLVM（数百 MB）、每次启动都有
秒级编译延迟、内核一升级脚本就可能编译失败。Andrii Nakryiko
后来总结的三大代价——**编译延迟、内核头依赖、内存占用**——
指向同一个结论：必须"**在我机器上编译一次，拷到任意内核上运行**"。

难点在 tracing：程序要读 `task_struct` 这类**内核内部结构体**，
而每个内核版本的字段偏移都可能不同。硬编偏移就是回到 LKM 的老路。
破局方案分三步落地：

```
  "一次编译，到处运行"（CO-RE）三块拼图
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │ BPF 程序自带  │  │ 加载器拿着程序 │  │ 运行期按重写  │
  │ 类型信息(BTF) │  │ BTF 与当前内核 │  │ 后的偏移安全  │
  │ + 字段重定位  │─▶│ BTF 逐字段匹配 │─▶│ 读取目标字段  │
  └─────────────┘  └─────────────┘  └─────────────┘
   (编译期,5.4起     (加载期一次)      (运行期零成本)
    内核自带BTF)
```

配套的还有全局变量（5.1，配置下发不再靠 map 舞蹈）、100 万指令
上限与有界循环（5.2/5.3，终于能写 `for` 循环了）。libbpf + CO-RE
从此成为事实标准——这也是今天我们用 cilium/ebpf 时"为什么 .o 文件
里要带 BTF 段"的历史原因（第 12 章展开）。

### 阶段三：从"功能"到"工程"（5.5-6.x，2020 至今）

- **fentry/fexit 与 trampoline（5.5）**：观测从"断点陷阱"升级为
  "直接调用"，近零开销且类型安全（第 10-11 章的完整对比）；
- **BPF link（5.7）与 LSM 程序（5.7）**：挂载关系成为内核对象、
  eBPF 正式进入安全策略领域（Tetragon/Falco 的土壤）；
- **ringbuf（5.8）与 CAP_BPF（5.8）**：事件通道换代、权限细分；
- **工程化补全（5.10-5.18）**：可睡眠程序、memcg 计费（memlock
  时代结束）、bpf_timer、multi-kprobe；
- **当下（6.6+）**：tcx 重塑 TC 挂载，user ringbuf/arena 探索
  新的交互面。

树状归纳（三条轴线如何长出今天的形态）：

```
                eBPF（3.18 地基）
   程序类型轴 ──────────────┼────────────── map 类型轴
   SOCKET_FILTER            │            ARRAY/HASH
   kprobe·tc(4.1)           │            PROG_ARRAY(4.2)·PERCPU(4.6)
   XDP(4.8)·cgroup(4.10)    │            LRU(4.10)·LPM(4.11)
   fentry(5.5)·LSM(5.7)     │            SOCKMAP(4.14)·RINGBUF(5.8)
   tcx(6.6)...              │            BLOOM(5.16)·user-ringbuf(6.8)
                            │
                     helper 轴：cBPF 0个 → 今天 200+
                     （map操作/包改写/tracing读取/打印/时间/...）
```

## 1.7 小结与练习

**小结**：cBPF（1992）确立了"用户态编译、内核态安全执行字节码"
的架构；eBPF（2014）用验证器说服了内核社区，用 map 补上了数据
短板；十年间沿"程序类型 × map 类型 × helper"三条轴线长成覆盖
网络/观测/安全的体系。安全模型的本质差异：**LKM 运行时爆炸，
eBPF 加载时证明**。

**练习**：
1. 在你的机器上 `tcpdump -d 'tcp port 22'`，观察过滤表达式被编译
   成的 cBPF 指令——亲眼看看 1992 年的虚拟机长什么样；
2. `uname -r` 查内核版本，对照 1.4 的时间线列出你的内核拥有哪些
   能力（先凭时间线推断，第 15 章再用 bpftool 验证）；
3. 思考题：1.1 的工单里，为什么"tcpdump 关联进程"这条路在原理上
   就走不通（提示：包与进程的上下文在哪一层开始分离）？
