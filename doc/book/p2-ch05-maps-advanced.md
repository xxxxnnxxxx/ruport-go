# 第 5 章 更快、更大、更稳

> 上一章的数据通道在低压力下完美。现在把压力加上去：8 核机器上
> 每秒百万个包、十万条会话、用户态要求全表扫描——三个问题依次
> 浮现：计数丢失、表满拒绝、迭代变慢。本章逐个击破，每个解法都
> 从"问题的物理本质"推导出来，而不是背结论。

## 5.1 计数为什么抖：并发与 per-CPU

### 5.1.1 复现与解剖

第 2/4 章的计数器在多核上有轻微丢失。用压力脚本复现（iperf 打满
网卡 30 秒），对比"内核内累计值"与"按包数推算值"，会发现少了
百分之零点几。根因是 `*cnt += 1` **不是原子的**——它是三条机器
指令（读、加、写），两个 CPU 可以交错执行：

```
 竞争时序（两个 CPU 同时 +1，结果却只加了 1）
 时刻   CPU0                          CPU1
 ─────────────────────────────────────────────────
 t1    读 cnt → 100
 t2                                   读 cnt → 100      ← 读到的还是旧值！
 t3    写 cnt = 101
 t4                                   写 cnt = 101      ← 覆盖了 CPU0 的结果
 ─────────────────────────────────────────────────
       两个包，计数只 +1。每秒百万包时，丢失肉眼可见
```

### 5.1.2 两条解法路线

**路线一：原子指令**（改动最小）。内核 BPF 提供原子内建：

```c
__sync_fetch_and_add(cnt, 1);     // 生成原子 add 指令，读改写不可分割
```

适合：value 结构里有**个别字段**需要并发累加（ruport 若要在
hash value 里做计数，就用这个）。代价：多核仍是同一缓存行上的
争用（cache line 弹跳），极高频时仍有开销。

**路线二：per-CPU map**（治本）。既然争用来自"多核抢同一格"，
那就**每核一格，天然无锁**：

```
 PERCPU_ARRAY：每个 CPU 一份独立 value 空间
               CPU0          CPU1          CPU2
              ┌─────┐       ┌─────┐       ┌─────┐
  key=0   →   │ 57  │       │ 43  │       │ 61  │   内核侧每个核只写自己
              └─────┘       └─────┘       └─────┘   的格子 → 零争用、零同步
                    ▲
              用户态读出 []uint64{57,43,61}，求和=161
```

动手升级第 2 章计数器（C 侧只改一个单词）：

```c
- __uint(type, BPF_MAP_TYPE_ARRAY);
+ __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
```

内核侧代码**一个字都不用改**——`bpf_map_lookup_elem` 在 per-CPU
map 上自动返回"当前 CPU 的那格"。变化全在 Go 侧读取：

```go
// 普通数组：单个值
var v uint64
m.Lookup(uint32(0), &v)

// per-CPU 数组：切片！长度=CPU 数
var perCPU []uint64
if err := m.Lookup(uint32(0), &perCPU); err != nil { ... }
var total uint64
for _, v := range perCPU { total += v }   // 聚合在用户态完成
```

选型口诀：**高频写的计数器一律 per-CPU**；value 里的个别字段需要
并发改、但表本身不适合拆（如 hash 里的会话统计）用原子指令；
低频写（配置表）两者都不需要。

### 5.1.3 per-CPU 的两个暗礁

1. **体积**：实际占用 = `round_up(value_size, 8) × CPU 数 ×
   max_entries`——一个"看似"8 字节的计数器在 128 核机器上是 1KB；
2. **语义**：per-CPU 读到的各核值**没有全序保证**（读 CPU0 的同时
   CPU1 还在写），聚合结果允许瞬时不精确——对计数场景这是可接受
   的 trade-off，对"精确快照"场景不是（那就得回到原子方案）。

## 5.2 表满了怎么办：LRU 与容量规划

### 5.2.1 E2BIG 的两种死法

第 4 章练习 2 已让你见过 `bpf_map_update_elem` 插满后的失败。
真实系统里它有两种死法：

- **静默死**：忘了检查返回值——新会话悄悄丢失，直到用户投诉；
- **雪崩死**：插入失败触发重试风暴。经典案例：用 hash 做"去重表"，
  扫描器灌满表后全部 update 失败，重试打满 CPU。

### 5.2.2 LRU：自动淘汰的 hash

`BPF_MAP_TYPE_LRU_HASH` 把行为改成"**满了自动赶走最久未使用的
条目**"：

```
 普通 HASH：max_entries=3
   插入D ──▶ E2BIG 拒绝（表已满：A B C）

 LRU_HASH：max_entries=3
   插入D ──▶ 淘汰最久未访问的 A ──▶ 表变为 B C D ✅
             （每个桶维护本地 LRU 链，近似全局 LRU——用精度换性能）
```

一行切换：

```c
- __uint(type, BPF_MAP_TYPE_HASH);
+ __uint(type, BPF_MAP_TYPE_LRU_HASH);
```

**适用判据**（三个都要满足）：条目**可牺牲**（老会话被踢无碍）、
访问有**时间局部性**（LRU 才有意义）、无法预知规模。conntrack 表、
NAT 表、`按 IP 统计`（活跃 IP 集合有限）都是标准场景；反之，
"路由表"这种每条都不可丢的，宁可容量规划做大普通 hash。

### 5.2.3 容量规划怎么算

容量不是拍脑袋：`max_entries ≈ 峰值速率 × 平均条目生命周期 ×
安全系数(1.5~2)`。例：100k pps 新建会话、条目平均活 30s →
300 万条起步——这个量级要么 LRU 要么分片多表，普通 hash 的预分配
内存（第 13 章 13.2 会算给你看）会大到不可接受。

## 5.3 十万条目怎么扫：迭代语义与批量

### 5.3.1 Iterate 的真相：游标，不是快照

用户态全表扫描（如每分钟 dump 一次会话表）用 `Iterate()`。但必须
清楚它底层是 `get_next_key` **游标推进**，不是拍快照：

```
 扫描期间表被并发修改时：
 ┌──────────────────────────────────────────────┐
 │ 你正在按"当前桶序"走：k1 → k2 → k3 → ...      │
 │ 内核侧同时：插入 kX（可能出现在你身后→漏看）    │
 │            删除 k3（你的游标指着它→跳到下一桶） │
 └──────────────────────────────────────────────┘
 结果：可能漏看新键、可能重复、可能跳键——都是合法行为
```

工程上有两种正确姿势：

1. **可容忍近似**（Top N 统计）：直接扫，接受瞬时误差；
2. **需要严谨**：**先收集全部 key，再逐个处理**——ruport 的
   `pollMessages` 就是这个模式（先 `Iterate` 收集 key 列表，再逐个
   `LookupAndDelete`），处理逻辑不依赖"扫描时刻的一致性"。

### 5.3.2 批量 API：一次系统调用搬一页

逐 key 操作 = 每条一次系统调用（syscall 开销 ~1μs）。10 万条目的
全表扫描光 syscall 就吃掉 100ms。5.6 起内核提供批量接口
（cilium 封装）：

```go
cursor := new(ebpf.MapBatchCursor)
keys := make([]uint32, 256)
vals := make([]uint64, 256)
for {
    n, err := m.BatchLookup(cursor, &keys, &vals, nil)
    if n == 0 { break }          // 扫完
    // 处理 keys[:n] / vals[:n]
}
```

一次 `bpf()` 搬一整页，吞吐量级提升。老内核上报
`ErrNotSupported`，用 `features.HaveBatchAPI()` 预判并降级到逐 key。

## 5.4 专为特定问题而生的类型

map 家族还有几个"专用工具"，见到对应问题时应条件反射：

**QUEUE / STACK（4.20+）**——内核→用户的异步传带数据的事件：

```c
struct event ev = {...};
bpf_map_push_elem(&q, &ev, BPF_EXIST);    // 内核侧入队
// 用户侧 Go:  m.LookupAndDelete? 用 peek/pop 语义（cilium 提供
//             LookupAndDelete 配合 queue 即 pop）
```

与 ringbuf（第 6 章）的分工：queue 无序保证但**逐条独立**、天然
背压（满了报错由你决策）；ringbuf 吞吐高但覆盖旧数据。

**LPM_TRIE（4.11+）**——最长前缀匹配，路由表的正确形态：

```c
struct { __uint(type, BPF_MAP_TYPE_LPM_TRIE);
         __uint(key_size, 8);             // 4字节前缀长 + 4字节IP
         __type(value, __u32);            // 例如下一跳
         __uint(max_entries, 1024);
         __uint(map_flags, BPF_F_NO_PREALLOC); } routes SEC(".maps");

struct key4 { __u32 prefixlen; __be32 addr; };   // 第一个字段必须是前缀长
```

lookup 自动按最长前缀命中（`10.0.0.0/8` 与 `10.1.0.0/16` 并存时
优先后者）。防火墙规则表、策略路由用它，比"遍历 hash 比掩码"
优雅且 O(深度)。

**其他一句话定位**（速查全表见附录 B）：`BLOOM_FILTER`(5.16+)
概率去重；`SOCKHASH/SOCKMAP` 存 socket 做重定向（第 9 章）；
`PROG_ARRAY` 存程序做尾调用接力（第 10 章用到的场景之一）。

## 5.5 小结与练习

**小结**：并发计数两条路——原子指令（局部字段）与 per-CPU（整表
治本，聚合挪到用户态）；容量用 LRU 解决"可牺牲条目的爆表"，用
容量公式规划不可牺牲的表；Iterate 是游标非快照，严谨场景先收集
key 再处理，规模上来换批量 API；queue/stack/LPM 各有其"本命问题"。

**练习**：
1. 用 `__sync_fetch_and_add` 改造第 4 章按 IP 统计的 `*cnt += 1`，
   压测对比丢失率；再换 per-CPU hash（`PERCPU_HASH`）对比——
   体会两者聚合方式的差别（提示：per-CPU hash 的 value 是切片，
   `lookup` 返回的是本核指针，Go 读出 `[][]uint64` 后按列求和）；
2. 把 4.3 的表换成 `LRU_HASH`、`max_entries=4`，灌 10 个 IP，
   用 `bpftool map dump` 观察"最老的谁被赶走了"；
3. 写一个 10 万条目的表，分别用逐 key 与批量扫描计时对比
   （没赶上 5.6 内核就记录 `ErrNotSupported` 的降级路径）；
4. 思考题：为什么 per-CPU map 不需要锁，而普通 hash 需要桶锁？
   用 5.1.1 的时序图推演 per-CPU 场景下同样的两个 CPU 会怎么走。
