# 第 3 章 与验证器初遇

> 每个 eBPF 开发者的记忆里都有同一天：程序第一次被验证器拒绝。
> 看不懂的日志、几百行的指令流、似乎不讲理的报错。本章把这天的
> 挫折变成你的核心能力——**读懂验证器在说什么**。它是 eBPF 与
> 其他所有"内核扩展"技术的分水岭：理解了验证器，eBPF 的所有
> 禁忌（先检查后访问、判空、有界循环）都会从"规矩"变成"显然"。

## 3.1 必然的遭遇战：程序被拒了

我们不回避失败，直接制造三起"事故"。以下程序都以第 2 章的
计数器为基础改坏一处，报错日志裁剪自真实内核输出。

### 事故一：不检查就读包（最高频）

```c
// 坏代码：没有边界检查直接读以太头类型字段
struct ethhdr *eth = data;
if (eth->h_proto == bpf_htons(ETH_P_IP)) {   // ← 直接解引用！
    ...
}
```

加载时 `LoadAndAssign` 返回：

```
process 42: 0: (61) r2 = *(u32 *)(r1 +0)
1: (bf) r1 = r2
2: (07) r1 += 14
3: (69) r1 = *(u16 *)(r1 +12)      ← 在这里被拦下
R1 invalid mem access 'inv'        ← 注意这个 'inv'
```

关键在最后一行：`R1` 的类型是 `inv`（invalid/unbounded scalar）——
验证器认为"这是一个来源不明的数字"，而**拿数字当地址解引用是
禁止的**。要让它变成合法指针，必须先经过边界检查（3.5 节）。

### 事故二：使用未初始化的变量

```c
// 坏代码：ext 没赋值就拿去算 key
struct msg m;
__u32 idx = m.field;          // ← m 是栈上未初始化的内存
```

```
8: (61) r1 = *(u32 *)(r10 -8)
invalid read from stack off r10-8+0 size 4
```

`r10` 是栈帧指针（第 4 章的角色表）——验证器逐字节跟踪栈上的
每一格"是否写过"，读没写过的格子直接拒绝。修复：定义时初始化
`struct msg m = {};`。

### 事故三：循环边界证明不了

```c
// 坏代码：循环次数来自包内容（攻击者可控）
__u8 n = iph->ttl;
for (__u32 i = 0; i < n; i++) { ... }   // ← n 是多少？验证器不知道
```

```
11: (15) if r2 == 0x0 goto pc+6
...
loop detected: insn 11-17 ...       （示意；5.3 前内核则直接报 back-edge）
```

5.3 起内核允许循环，但**必须证明循环次数有上界**。"包里读出来的
字节"无法提供保证，拒绝。修复：换成编译期常量上界，或先
`if (n > 16) return XDP_PASS;` 收紧范围。

三起事故的共同点值得品一下：**验证器不评估你的意图，只证明你的
程序对任意输入都安全**。这三类（越界/未初始化/无界）覆盖了新手
90% 的被拒场景。

## 3.2 读懂拒绝信：verifier 日志导读

拒绝信不是乱码，它是**一份带注释的指令流 + 寄存器状态快照**。
先看cilium/ebpf怎么把它拿全（默认失败时 error 字符串里已带日志；
主动看全文用选项）：

```go
coll, err := ebpf.NewCollectionWithOptions(spec, ebpf.CollectionOptions{
    Programs: ebpf.ProgramOptions{
        LogLevel:     ebpf.LogLevelBranch | ebpf.LogLevelStats, // 5.2+
        LogSizeStart: 1 << 16,
    },
})
// 成功加载也能看：coll.Programs["count_packets"].VerifierLog
```

一份日志的解剖图（用第 2 章计数器开头几条指令的真实形态）：

```
  指令号   指令本体                      ← 你写的 C 编译后的 BPF 汇编
 ┌──────────────────────────────────────────────────────┐
 │ 0: (61) r2 = *(u32 *)(r1 +0)        ; r1 是入口参数 ctx │
 │ 1: (61) r3 = *(u32 *)(r1 +4)                          │
 │ 2: (bf) r1 = r2                                       │
 │ 3: (07) r1 += 14                                      │
 │ 4: (2d) if r1 > r3 goto pc+12        ; 我们的边界检查   │
 │    R1_w=inv(id=0) R2_w=inv(id=0) R3_w=inv(id=0) ◀──┐  │
 │                                   到达此指令时的寄存器状态│
 │ 5: (bf) r4 = r2                    ;（ctx 读取被重写后）│
 │ 6: (69) r5 = *(u16 *)(r4 +12)      ; 读 eth->h_proto   │
 └──────────────────────────────────────────────────────┘
 末尾统计（LogLevelStats，5.2+）：
   processed 57 insns (limit 1000000) max_states_per_insn 2
   total_states 13 peak_states 13 mark 12
```

三个阅读层次：

1. **指令行**：`编号: (十六进制操作码) 汇编`。对着
   `llvm-objdump -d count.bpf.o` 的输出，几乎逐行对应；
2. **状态行**（缩进的 `R1_w=...`）：到达该点时每个寄存器的"身份
   证"——类型（`inv` 未知数 / `pkt` 包指针 / `map_value` …）+
   数值范围。**这是理解验证器的钥匙**，3.4 节整节演示；
3. **统计行**：`processed ... limit 1000000`——接近上限说明
   路径爆炸（常见于循环或大量分支），解法是简化程序结构而不是
   调参数。

报错本身出现在被拦下的那条指令之后，格式
`invalid access to packet, off 14 size 14, R2(id=2, off=14, r=0)`：
`off 14`（想从偏移 14 开始）`size 14`（读 14 字节）`r=0`（当前
只被证明可读 0 字节）——**三个数字一减，答案自己出来：先证明
再访问**。

## 3.3 安全审查官：验证器的职责与思维

### 3.3.1 它要证明什么

验证器的职责清单（对应它拒绝你的一切理由）：

| 要证明 | 对应拒绝 |
|---|---|
| 程序**必然终止**（无死循环） | loop detected / back-edge |
| 所有内存访问在界内 | invalid access to packet/stack/map |
| 所有寄存器先写后读 | invalid read / !read_ok |
| 指针不泄露给用户态 | R0 leaks addr |
| helper 调用参数类型/个数合法 | invalid arg |
| 栈不溢出（512B）、指令数不超限 | too large / stack limit |

### 3.3.2 它怎么思考：符号执行 + 状态剪枝

验证器不看测试运行，它**在加载时把你的程序"纸上推演"一遍**：

```
            验证器的思维模型（符号执行）
                          ┌──▶ 分支A状态：r1>data_end（跳走，推演 PASS 路径）
 指令4: if r1 > r3 ───────┤
                          └──▶ 分支B状态：r1<=data_end（继续，且记住这个事实）
                                 │
 指令5: 读 *(r1+12)             │ 站在B状态下检查：
                                 │  "r1 有没有资格读 12+2 字节？"
                                 │   → 查状态：r1 = r2+14 且 r2+14<=r3
                                 │   → 资格成立 ✅ 放行
 探索完整棵"执行树"且全部安全 → VERIFIED → 允许 JIT
```

两个工程细节让它现实可行：

- **状态剪枝**：同一条指令若第二次到达时寄存器状态与已记录的
  等价，停止再探索（否则一个 `if` 循环组合就能让路径数爆炸）。
  统计行的 `total_states/peak_states` 就是剪枝的痕迹；
- **复杂度上限**：最多验证 100 万个状态；超限报
  `BPF program is too large`——这是"证明义务"的兜底。

### 3.3.3 一个常见的误解

"我包长肯定够，为什么还拒绝我？"——因为验证器**不做运行时假设**。
它面对的是"所有可能的输入"：0 字节的包、带 IP 选项的包、恶意
构造的偏移。你的"肯定够"必须写成它认的形式——**显式的比较
指令**。这就是为什么包解析代码永远长这个样子。

## 3.4 完整状态推演：第 2 章程序的开头八条

现在把 3.2 的钥匙用起来。逐指令推演 `count_packets` 的开头
（简化自真实日志，只保留关键状态）：

```
 指令                        推演后的寄存器状态            说明
 ─────────────────────────────────────────────────────────────
 0: r2 = *(u32 *)(r1+0)     R1=ctx  R2=inv              从 ctx 取 data：
                                                            合法（ctx 可读）
 1: r3 = *(u32 *)(r1+4)     R3=inv                       同上，取 data_end
 2: r1 = r2                 R1=inv(=data数值)             拷贝
 3: r1 += 14                R1=inv(data+14)              纯算术，还是数字

 4: if r1 > r3 goto +12     分裂成两个世界：
    ├─真：r1>r3            → 走 PASS 支路（安全，不再关心）
    └─假：r1<=r3           → 继续，并且【事实 r2+14<=r3 被记住】

 5: r4 = r2                 R4=inv
    ★ 点石成金 ★
    加载器早已把 0/1 两条指令重写为"包指针专用读取"
    （convert_ctx_access），此刻验证器据此升级类型：
                            R2=pkt(off=0, r=14)
                            R4=pkt(off=0, r=14)
    含义：合法包指针，当前偏移0，已被证明可读 14 字节

 6: r5 = *(u16 *)(r4+12)    检查：12+2=14 ≤ r=14 ✅
                            R5=inv(读到的h_proto值)
 7: ...                     之后所有对包的访问都基于 r=14 继续谈判
```

**把这张表读懂，验证器就再也不是黑盒**。回头解释 3.1 事故一：
没有指令 4 的比较，指令 6 处 `r4` 的状态是 `pkt(off=0, r=0)`——
`12+2 > 0`，报 `invalid access to packet, off 12 size 2, R4(r=0)`。

那行报错的三个数字，现在对你来说已经是"验算题"了。

## 3.5 包访问铁律与两个标准模式

铁律一句话：**每次解引用前，验证器必须"看得见"一次覆盖该访问的
边界检查**。两个覆盖全书所有示例的标准模式：

**模式一：检查头指针**（定长头，第 2 章用法）

```c
struct ethhdr *eth = data;
if ((void *)(eth + 1) > data_end)   // eth+sizeof(ethhdr) 在包内？
    return XDP_PASS;
// 此后 eth 的所有字段（偏移 0~13）可安全访问
```

**模式二：一次证明一大段**（定长载荷，ruport 用法）

```c
// 需要读 12 字节魔术标记 + 110 字节消息体？
if ((void *)(pdata + 12 + sizeof(struct Message)) > data_end)
    return XDP_PASS;
// 之后这一段的每次访问都被覆盖，无需再检查
```

**变长头的再检查**（IP/TCP 选项）：头长来自包内容时，指针跳到
下一层之前必须**用新长度再证明一次**：

```c
struct iphdr *iph = (void *)(eth + 1);
if ((void *)(iph + 1) > data_end)          // 先证明基本 IP 头
    return XDP_PASS;
struct tcphdr *tcph = (void *)iph + iph->ihl * 4;   // ihl 来自包！
if ((void *)(tcph + 1) > data_end)         // ★ 必须重新检查
    return XDP_PASS;
unsigned char *payload = (void *)tcph + tcph->doff * 4; // doff 同理
if ((void *)(payload + 128) > data_end)    // ★ 再检查
    return XDP_PASS;
```

ruport 的 XDP 程序就是这三段式的实战完整版（第 17 章 17.2）。

## 3.6 常见拒绝 TOP5 速查

| # | 报错关键词 | 根因 | 修复 |
|---|---|---|---|
| 1 | `invalid access to packet ... r=N` | N 不够本次读取 | 3.5 两模式补检查 |
| 2 | `invalid read from stack` / `!read_ok` | 读未初始化栈/寄存器 | `= {}` 初始化；先写后读 |
| 3 | `loop detected` / `back-edge` | 循环无上界证明 | 常量上界或先 clamp 输入 |
| 4 | `invalid mem access 'inv'` | 拿数字当指针解引用 | 该值需来自 ctx/map/helper |
| 5 | `R0 leaks addr into map/return` | 指针（或其数值）外泄 | 传 ID/index，别传地址 |

排障动线：**定位报错行的指令号 → 对照 objdump 找到源码位置 →
按"它要什么证明"补**。第 15 章会给出完整调试体系，本章的"读日志"
是其中最核心的一环。

## 3.7 小结与练习

**小结**：验证器是符号执行器，加载前对所有输入证明安全终止；日志
= 指令流 + 寄存器状态快照，`pkt(off,r)` 的 `r` 是你的"信用额度"；
包访问铁律"先证明、后访问"有三个标准模式（定长头/定长段/变长头
逐层再证明）。被拒不是刁难，是验证器在替未来的你挡住内核 panic。

**练习**（第 2 章程序基础上）：
1. 删掉以太头检查，加载，把报错日志的 `off/size/r` 三个数字抄下来，
   按本文方法验算一遍；
2. 把协议分桶改成先读 `iph->ttl` 做循环上界（复现事故三），观察
   不同内核版本的报错差异；
3. 写一个"读 map 值当指针用"的程序（事故四变体），看报错用词；
4. 开 `LogLevelBranch|LogLevelStats` 成功加载第 2 章程序，找到
   `total_states`，然后给程序加一个无关的 `if` 分支，观察状态数
   变化——亲手感受"路径"。
