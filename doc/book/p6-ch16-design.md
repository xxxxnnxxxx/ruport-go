# 第 16 章 从需求到架构：设计一个端口复用系统

> 本章不出现成规模的代码。我们只做一件事：拿着需求清单，用
> 前十五章学过的知识**一步步推演出 ruport 的架构**——当第 17
> 章打开真实代码时，你会发现每个设计决定都"本该如此"。

## 16.1 需求还原：隐秘服务如何借道开放端口

场景设定（红队授权演练背景，本仓库为该场景的教学实现）：

> 目标服务器对外只开放 80/tcp（一个正常运行的 Web 服务，不能
> 干扰）。演练方需要在这台服务器上激活一条**隐秘通道**：控制端
> 能随时通过**同一个 80 端口**与目标上的一个内部服务建立通信，
> 并可下发"反弹连接 / 执行命令"等指令；通道可动态建立与撤销。

把需求拆成可检验的约束清单：

```
 C1 不影响 80 端口上的正常 Web 业务（无感）
 C2 不新开任何监听端口（netstat/ss 不出现新服务）
 C3 控制指令能"藏"在发往 80 的普通 TCP 流量里送达
 C4 指令通道与数据通道都要可动态开关（增/删）
 C5 单二进制、无第三方运行时依赖（C 程序的部署约束→Go 的理由）
```

对照本书知识给每条约束找"技术落点"：

| 约束 | 落点 | 出处 |
|---|---|---|
| C1 | 观察型钩子 + XDP_PASS；改写只对**命中路由的流**生效 | 第 7 章 |
| C2 | 不监听端口——复用 80；内部服务只绑本机/仅对改写后的包可见 | 第 8 章 |
| C3 | 正常流量里识别"特征包"→ 嗅探程序 + map 消息队列 | 第 4/6 章 |
| C4 | map 即策略：控制面增删路由，数据面查表改写 | 第 4/7 章 |
| C5 | cilium/ebpf + bpf2go：单二进制嵌 .o | 第 14 章 |

## 16.2 架构推演：为什么是三件套

### 16.2.1 从第 8 章的雏形出发

第 8 章你已经写过端口复用的雏形：ingress 把 8080 改到 80、
egress 改回去。它离本需求差三步：

```
 雏形                          本需求
 固定端口对(8080↔80)     ──▶  动态：哪条流改到哪，运行时决定
 单一硬编码规则          ──▶  可增删的多条路由（C4）
 没有"指令"概念          ──▶  要有指令通道 + 可执行动作（C3）
```

### 16.2.2 三个组件，逐个推演

**推演一：指令怎么进来？（→ 嗅探层）**

给被控端下指令的朴素办法是开个新端口——违反 C2。换个思路：
**指令就藏在对 80 的正常访问里**。控制端向 80 发起一个普通 TCP
连接，payload 里带上特征标记 + 指令体；被控端在内核里"旁听"
所有包，认出特征即收件。

在哪个钩子旁听？对照第 7 章收包地图：越早越便宜、且我们**只想
听不想动**——XDP 是自然选择（`XDP_PASS` 恒返回，业务无感满足
C1）。收到的指令写进一张 map（消息队列语义：**取出即删**，
第 4 章 4.4）——`message_map` 诞生。

**推演二：数据面怎么改写？（→ 改写层）**

控制端后续的通信流要在 80 与内部服务之间"换港口"。改包需要
`bpf_skb_store_bytes/`l4_csum_replace`（第 8 章手术三步）——这些
helper 只有 TC/cgroup 侧有 → **TC 双向挂载**：ingress 改目的端口
（进入内部服务），egress 改源端口（回到 80 闭环）。改写规则不能
写死 → 一张**路由表 map** 驱动——`router_map` 诞生。

**推演三：谁做决策与执行？（→ 控制层）**

收到指令后要判断"加路由还是删路由、要不要起反弹进程"——这些
逻辑（读配置、fork 进程、记 pid、发信号）在内核态写是自讨苦吃
（第 1 章 LKM 教训的微缩版）。**用户态 Go 程序**轮询 message_map、
写 router_map、按需执行动作——控制面/数据面分离（第 2 章 2.1
的纪律）。

### 16.2.3 全景架构图

三个推演合体：

```
                        ┌──────────── 被控端 ────────────────┐
 控制端 c3               │                                     │
 ──TCP:80──▶ ┌──────────┼──────────────────────────────┐     │
  指令包      │ ★XDP 嗅探 │ 认出魔术包 → message_map       │     │
             │  (PASS)   │                              │     │
             ├──────────┼──────────────────────────────┤     │
             │ 正常Web流量│────────▶ 80端口 Web 服务       │     │
             │          │   （无感，C1 ✓）               │     │
             └──────────┼──────────────────────────────┘     │
                        │        ▲ 每秒轮询/取出即删            │
                        │  ┌─────┴──────┐                     │
                        │  │ cmd/ruport │ Go 控制面            │
                        │  │ 判定/执行    │──写──▶ router_map   │
                        │  └────────────┘          │          │
                        │ ★TC ingress ◀──查表改 dst│          │
                        │   （80→内部端口）          │          │
                        │ ★TC egress ◀──查表改 src  │          │
                        │   （内部端口→80）          │          │
                        │      ▲                    │          │
                        │   内部服务（如 ssh/反弹）◀──┘          │
                        └─────────────────────────────────────┘
```

把三张熟悉的地图叠上去验证：XDP 在第 7 章地图的位置 ②、TC 在
③/④（双向）、Go 控制面是第 2 章三段式的"左半边"。**ruport 没有发明
任何新架构，它只是把三个学过的模式拼对了位置。**

## 16.3 数据契约设计

三个组件之间靠两份"契约"协作——契约即接口，先于代码存在。

### 16.3.1 契约一：124 字节指令消息（c3 ↔ XDP）

发往 80 的指令包，TCP payload 前 124 字节布局：

```
 偏移   长度   字段          语义
 ───────────────────────────────────────────────────────
 0      2     s1           ┐ 魔术标记：s1²+s2²=s3（小端）
 2      2     s2           │ s1/s2 为随机奇数 → 每次包字节都不同，
 4      8     s3           ┘ 降低特征匹配概率（C3 的"隐"）
 12     1     ins 低字节    功能码：01 加路由/02 反弹/03 shell/04 扩展
 13     1     ins 高字节    ≠0 表示"删除"（复用同一帧格式表达撤销）
 14     4     cip          控制端 IP（网络序）
 18     2     cport        控制端端口（网络序）
 20     2     connport     出网端口 p1（可 0=未知，见端口学习）
 22     2     nativeport   内部服务端口 p2（加路由时必填）
 24     100   ext          扩展载荷（反弹类型名 / shell 命令串，NUL 结尾）
```

设计取舍两讲：**为什么用毕达哥拉斯式标记而不是固定 magic 数**——
固定 magic（如 0xDEADBEEF）一次特征库就死；`s1,s2` 每包随机，
校验式成立才认，代价只是 12 字节。**为什么删除复用高字节**——
一帧格式表达增/删，解析器只需一份（对照第 17 章的 HandleRouter，
hi>0 走删分支）。

### 16.3.2 契约二：路由表（Go ↔ TC）

```c
struct Router {            // value（10 字节，pack(1)）
    __be32 cip;            // 控制端 IP
    __be16 cport;          // 控制端端口
    __be16 connport;       // 出网端口（egress 改写的目标）
    __be16 nativeport;     // 内部服务端口（ingress 改写的目标）
};
// key = (cip << 16) | cport   ← 网络序【原始值】拼装
//      内核与用户两侧用同一份原始值计算 → 天然一致，零转换（第4章推论）
```

### 16.3.3 端口学习：为什么两个端口字段都可能"未知"

c3 下发指令时未必知道被控端的实际出网端口（比如控制端只写了
"用 80 出网"，但真实源端口由内核分配）。于是路由表的两个端口
字段被设计成**可学习**的半状态：

```
 初始（c3 未指定 connport）：connport=0
   TC egress 看到该流真实源端口 → 回填 connport（egress 学）
 初始（nativeport 已知）：直接改写
   若为 0：TC ingress 看到真实目的端口 → 回填 nativeport（ingress 学）
 完整闭环后：两字段皆非零，改写稳定进行
```

一张时序图看懂一条指令的完整一生（含学习）：

```
 控制端                    被控端
   │ ① 指令包(魔术+加路由+nativeport=22)   │
   ├──────────────TCP:80────────────────▶│ XDP 认包 → message_map
   │                                      │ Go 轮询取出 → router_map 插入
   │ ② 后续业务流 dst=80                  │
   ├─────────────────────────────────────▶│ TC ingress: dst 80→22
   │                                      │   （connport=0 → 学得 80）
   │ ◀────────────────────────────────────┤ ssh 服务回包 src=22
   │ ③ 回包看起来 src=80（闭环）           │ TC egress: src 22→connport(80)
   │                                      │
   │ ④ 删除指令（ins 高字节=1）            │
   ├─────────────────────────────────────▶│ message_map → Go 删 router_map
   │                                      │ （如属反弹类还 kill 子进程）
```

架构与契约都已推演到位。第 17 章，逐行对答案。

## 16.4 小结与练习

**小结**：五条约束各自映射到已学机制（无感=XDP PASS/复用=TC 双向
改写/指令=特征包+消息 map/动态=map 即策略/部署=bpf2go）；三件套
=嗅探（XDP+message_map）+改写（TC+router_map）+决策（Go 控制面）；
两份契约先于代码：124 字节指令帧（随机魔术+复用高字节表达删除）、
路由表（原始值 key + 双字段端口学习）。架构没有发明，只有拼装。

**练习**（动笔前的思想实验，第 17 章对答案）：
1. 嗅探层为什么不用 TC ingress 而用 XDP？给出至少两条理由，再
   说出一条"用 TC ingress 也行"的理由（开放题）；
2. 指令帧如果只要求"控制端→被控端"单向，为什么消息通道还要
   用 hash map 而不是 ringbuf？（提示：消费者是谁、要不要取出
   即删的握手语义——第 6 章结尾的推/拉之辨）；
3. 设计题：若要求支持**多个控制端同时各持一条路由**，现有
   key 设计哪里已经天然支持？哪里会成为瓶颈？
