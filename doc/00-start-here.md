## 1. eBPF 到底是什么

**一句话**：eBPF 是 Linux 内核提供的**可编程沙箱**——你把一小段经过
静态验证的字节码交给内核，内核在指定事件发生时（来了一个包、触发
了一次系统调用、执行到某个内核函数……）替你执行它，全程不需要改
内核源码、不需要写内核模块、不需要重启。

三个类比帮新手定位：

| 类比 | 对应关系 | 局限 |
|---|---|---|
| eBPF 之于内核 ≈ **JavaScript 之于浏览器** | 网页不允许直接操作硬件，浏览器给一个受限沙箱跑你的脚本；内核不允许随便加载代码，eBPF 给一个验证过的沙箱跑你的字节码 | JS 解释执行慢，eBPF 是 JIT 本机码，几乎无损耗 |
| eBPF ≈ **内核里的 WASM** | WASM：任何语言编译成安全字节码在任何平台跑；eBPF：C 编译成安全字节码在内核跑 | WASM 面向通用计算，eBPF 面向"事件驱动的内核观测/网络/安全" |
| eBPF ≈ **安全版内核模块** | 内核模块（LKM）也能往内核里塞代码，但一个 bug 就 panic 整机；eBPF 程序在加载前被验证器证明"一定安全终止、绝不越界" | LKM 全能力，eBPF 能力受限（见 §4） |

**为什么需要它**：改内核要走上游社区，周期以年计；LKM 崩溃代价是
整机；而不懂内核内部又做不了观测和定制。eBPF 用"**验证 + 受限执行**
换**安全可编程**"，把三者的矛盾拆开了。

四个名词，贯穿全套文档（心智模型的四根柱子）：

```
钩子(hook)   ——内核里预留的触发点："这种事发生时叫我的代码"
程序(program)——你写的那段逻辑（事件发生时干什么）
map          ——内核态↔用户态共享的键值存储（数据面）
加载器(loader)——用户态控制程序：编译、加载、挂载、读 map（控制面）
```

ruport-go 就是一个完整标本：XDP/TC 是钩子，`ruport_xdp.bpf.c`/
`ruport_tc.bpf.c` 是程序，`message_map`/`router_map` 是数据面，
`cmd/ruport` 是控制面。

## 2. eBPF 能做什么（能力全景）

按四大应用领域组织。每格给"能力"和"代表项目"，帮你判断"我想做的
事属于哪类、有没有现成轮子"。

### 2.1 网络：在内核协议栈的任意层处理包

| 能力 | 典型场景 | 代表项目 |
|---|---|---|
| 最早位置丢包/放行（DDoS 清洗、ACL） | 攻击流量在驱动层直接 DROP，skb 都不建 | Cloudflare 的 DDoS 防护 |
| 四层负载均衡 | VIP→后端映射，XDP REDIRECT | Facebook **Katran** |
| 容器/K8s 网络（Service、NetworkPolicy） | 每节点一套 BPF 替代 kube-proxy/iptables | **Cilium** |
| NAT / 端口复用 / 隧道封装 | 改包头+增量校验和（**ruport 干的事**） | 各家自研 |
| socket 级加速 | 同机通信绕过协议栈（sockmap 直达） | Cilium 加速 Service |
| 流量分类/QoS | tc 分类器天生职责 | tc 社区 |

*场景故事*：机房受到 SYN flood，老办法是 iptables 逐条匹配（包已经
走过半个协议栈才被丢）；换成 XDP 程序，包在网卡驱动层直接被丢弃，
单核可挡千万级 pps，CPU 几乎无感。

### 2.2 观测（tracing）：看见内核与进程的一切

| 能力 | 典型场景 | 代表项目 |
|---|---|---|
| 函数级探针（进/出任意内核函数） | "read() 到底慢在哪一层" | **bpftrace**、BCC 工具集 |
| 一次性问题抓现场 | 按条件（PID/端口/延迟阈值）记录事件 | bpftrace/自研 |
| 持续性能剖析（on-CPU/off-CPU/内存） | 生产环境常驻火焰图数据源 | **Parca**、Pixie |
| 网络观测（重传/RTT/丢包归因） | TCP 状态机事件流 | Cilium **Hubble**、pcapvisor |

*场景故事*：一句话回答"哪个进程在疯狂读 /etc/passwd"：

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat /str(args->filename)=="\/etc\/passwd"/ { printf("%s pid=%d\n", comm, pid); }'
```

这条命令背后就是"tracepoint 钩子 + BPF 程序 + ringbuf 上报"，和我们
doc/06 例 3 的结构一模一样。

### 2.3 安全：把策略放进内核执行

| 能力 | 典型场景 | 代表项目 |
|---|---|---|
| syscall 审计（谁、何时、对什么文件） | 文件完整性监控、数据外发检测 | **Falco** |
| LSM 钩子策略（权限判定的最底层） | 容器逃逸防护、权限提升阻断 | **Tetragon**、Tracee |
| 网络 + 进程关联取证 | "这个连到外网的进程是谁起的" | Tetragon |

*场景故事*：容器里的进程尝试 `execve` 一个 shell——传统方案要等审计
日志（事后）；BPF 在 `security_bprm_check` LSM 钩子上直接判定并阻断
（事中），且策略可热更新。

### 2.4 控制与定制：改变内核行为本身

| 能力 | 典型场景 | 代表项目 |
|---|---|---|
| cgroup 级网络策略/限速 | 容器带宽控制 | systemd/cgroup v2 生态 |
| 自定义 TCP 拥塞控制算法 | 用 BPF 实现 struct_ops（如 DCTCP 变体） | 内核 `struct_ops` |
| 内核结构体按需 dump | `cat` 一个 BPF iter 就能输出内核表 | bpf_iter |
| 定时/异步逻辑 | bpf_timer 延迟任务 | 5.15+ |

### 2.5 能力速查：想干 X，用哪个钩子

| 我想…… | 钩子/类型 | 详见 |
|---|---|---|
| 尽早丢/改/转发包 | XDP | 01/05/11 |
| 进协议栈前改包、镜像 | TC ingress/egress | 01/05/11 |
| 跟踪一次系统调用 | tracepoint（稳定） | 11 §5.2 |
| 跟踪某个内核函数内部 | kprobe（易碎）/fentry（BTF 化） | 05/11/13 |
| 跟踪用户态函数 | uprobe | 05 |
| 容器/进程组维度管控 | cgroup 系列 | 11 §4 |
| 安全策略判定 | LSM | 05/11 |
| 选 socket/改 socket 行为 | SK_LOOKUP/SOCK_OPS | 11 §1 |
| 周期性任务 | PERF_EVENT / bpf_timer | 11 §5.3 |

## 3. 系统的什么地方可以 hook（全景地图）

这是新手最缺的一张图。按"**沿一条数据流走一遍**"来记：包的收、包
的发、一次系统调用，三条主线覆盖 90% 的钩子。

### 3.1 主线一：一个网络包的一生（收包方向）

```
 ① 网卡硬件收到帧，DMA 进内存，硬中断
        │
 ② 驱动 NAPI 轮询取包
        │
        ├─★ XDP(native) ─────────── 全链路最早的钩子（skb 尚未创建）
        │     能做：XDP_DROP(丢弃,最快防火墙)/XDP_TX(原网卡弹回)/
        │           XDP_REDIRECT(转发他处)/XDP_PASS(放行)/改包头
        │     驱动不支持时退到 generic 模式（skb 已建，位置稍晚）
        ▼
 ③ __netif_receive_skb（进入内核协议栈入口）
        │
        ├─★ TC ingress(clsact) ──── 进协议栈前的最后一个改包点
        │     能做：改写/NAT/镜像/重定向/标记，改完送回正常处理
        │     ruport 在这里把"对外端口"改写成"本地真实服务端口"
        ▼
 ④ netfilter 钩子（iptables/nft 的 PREROUTING 等，非 eBPF，对照用）
        │
        ▼
 ⑤ 路由判断：本机接收？转发？
        │
        ├─★ kprobe/fentry ──────── 以上任意内核函数都能插探针
        ▼
 ⑥ IP/TCP/UDP 层处理
        │
        ├─★ cgroup ingress ─────── 容器/cgroup 维度的包过滤
        ▼
 ⑦ socket 接收队列
        │
        ├─★ SK_LOOKUP ───────────  入向 socket 选择（reuseport 场景）
        ├─★ SOCK_OPS ──────────── 连接生命周期事件（建连/RTT/重传）
        ▼
 ⑧ 应用进程 read() 收到数据
        └─★ SOCKET_FILTER ───────  socket 级过滤/抓包
```

记忆要点：**越靠上越快、越靠下上下文越丰富**（XDP 时只有裸包+网卡
信息；到 socket 层连进程是谁都知道了）。选钩子 = 在"性能"和"信息
量"之间选位置。

### 3.2 主线二：一个网络包的一生（发包方向）

```
 ① 应用 write()/send()
        ▼
 ② socket 层（TCP 段生成、拥塞控制决策）
        ├─★ SOCK_OPS（按连接调参）/ ★cgroup egress（容器级放行）
        ▼
 ③ IP 层（选路由、netfilter OUTPUT/POSTROUTING）
        ▼
 ④ __dev_queue_xmit（进设备发送队列前）
        ├─★ TC egress(clsact) ──── 发包方向最后的改包点
        │     能做：加密/封装/QoS 分类/重路由；ruport 在这里把回包
        │     源端口改回"对外端口"，完成端口复用闭环
        ▼
 ⑤ qdisc 排队 → 驱动 → 网卡发出
```

### 3.3 主线三：一次系统调用的一生（以 read() 为例）

```
 用户态:  read(fd, buf, len)
        │  syscall 指令（用户态→内核态切换）
        ▼
 ★入口观测（三选一，参数都能拿到）
    · tracepoint: syscalls/sys_enter_read   ← 稳定接口，推荐
    · kprobe:     __x64_sys_read            ← 函数名随内核版本变
    · fentry:     __x64_sys_read            ← BTF 化，类型安全(5.5+)
        ▼
 内核执行路径：VFS → 具体文件系统 → 块层 → …
    ├─★ 路径上任意内核函数都可 kprobe/fentry（如 vfs_read→…）
    ├─★ LSM 钩子（如 security_file_open）：权限判定点，可改结果
    ├─★ 普通 tracepoint（如 net/netif_rx 这类静态埋点）
        ▼
 ★出口观测
    · tracepoint: syscalls/sys_exit_read    ← 拿返回值
    · kretprobe / fexit                     ← fexit 还能同时拿参数(13章)
        ▼
 返回用户态，read() 返回
```

### 3.4 其他钩子面（不在三条主线上）

| 钩子面 | 触发时机 | 用途 |
|---|---|---|
| cgroup 事件族 | connect/bind/sendmsg/getsockopt… | 容器网络策略、地址改写 |
| perf 事件 | 定时器、PMU 硬件计数、自定义采样 | 周期性采集、性能剖析 |
| uprobe/USDT | 用户态二进制里的函数/探针点 | 应用层 tracing（无需改代码） |
| bpf iter | 用户 `cat` 时触发遍历 | dump 内核表/map |
| SK_SKB/SK_MSG | socket 消息收发路径 | sockmap 消息重定向 |

### 3.5 钩子稳定性分类（选型必看）

| 类别 | 钩子 | 跨内核版本 | 说明 |
|---|---|---|---|
| **稳定接口** | XDP、TC、tracepoint、cgroup、LSM、socket 族 | ✅ 基本不变 | UAPI 承诺，生产首选 |
| **动态探针** | kprobe/fentry 挂**内核内部函数** | ❌ 随版本漂移 | 函数被内联/改名即失效；fentry 至少类型安全 |
| **二进制耦合** | uprobe | ❌ 随目标二进制 | 重编译应用即失效；USDT 相对稳定 |

版本支持矩阵（哪个内核有哪个钩子）统一查 [09 章](09-kernel-versions.md)。

## 4. eBPF 不能做什么（能力边界）

限制不是缺陷，是"验证器能证明安全"的代价。背下这张清单，能避免
80% 的设计弯路：

| 限制 | 具体内容 | 影响/绕法 |
|---|---|---|
| 不能睡眠/阻塞 | 绝大多数上下文禁止（不可抢占的内核路径） | 不能直接做 IO/锁睡眠；5.10+ 少数类型可 `BPF_F_SLEEPABLE` |
| 不能调用任意内核函数 | 只能调 **helper 白名单**（按程序类型）+ kfunc | 想要的功能没有 helper → 用户态配合（map 交换） |
| 栈只有 512 字节 | 局部变量总量硬上限 | 大缓冲放 map/per-CPU 区 |
| 指令数上限 | 100 万（<5.2 内核 4096） | 超了拆尾调用 |
| 循环必须有界 | <5.3 完全禁止；之后验证器须证明有界 | 固定上界 `for(i=0;i<N;i++)` |
| 无浮点 | 不能用 float/double | 定点运算替代 |
| 不能递归 | BPF-to-BPF 调用深度 ≤8 | 迭代改尾调用（≤33 层） |
| 内存访问受限 | 指针必须来自 ctx/map/helper，且逐次验证 | 不能拿任意地址读内核（要 probe_read） |
| 不能泄露指针 | 指针数值不能返回用户态/存 map | 传 ID/index 代替 |
| map 容量有限 | 创建时定 max_entries（hash 满则 E2BIG） | LRU 淘汰或分片 |

一句话记住：**eBPF 程序是"事件处理小函数"，不是"内核里的通用程序"**。

## 5. eBPF vs 内核模块 vs iptables

| 维度 | eBPF | 内核模块(LKM) | iptables/nftables |
|---|---|---|---|
| 安全性 | 加载前验证，不可能 panic 内核 | 一个空指针=整机崩溃 | 安全（规则引擎） |
| 能力范围 | 观测/网络/安全/受限定制 | **全部**（任意内核能力） | 包过滤/NAT/有限匹配 |
| 可编程性 | C→受限字节码，图灵完备但受限 | 完整 C | 声明式规则 |
| 热更新 | 秒级（atomically 替换 link/程序） | 卸载重载（风险窗口） | 规则更新 |
| 性能 | JIT 本机码，XDP 为最高档 | 本机码 | 规则链线性匹配 |
| 内核版本耦合 | 稳定接口基本无耦合；探针有 | 强（每版内核重编） | 无 |
| 分发 | 单二进制嵌 .o（bpf2go） | 需对应内核头编译 | — |
| 适用 | 观测/网络策略/运行时安全 | 驱动、改内核核心行为 | 传统防火墙 |

选型直觉：**能 eBPF 就 eBPF；必须改内核核心行为才 LKM；纯静态包
过滤 iptables 仍够用**。

## 6. 心智模型总结与学习路线

五句话带走本章：

1. eBPF = **验证过的字节码 + 内核事件触发**，安全地扩展内核；
2. 一切应用 = **钩子（哪里）+ 程序（干什么）+ map（数据进出）**；
3. 钩子按数据流记：**收包、发包、系统调用**三条主线（§3 三张图）；
4. 能力边界是安全模型的一部分：**不睡眠、不越界、有界执行**（§4）；
5. 性能与信息量随钩子位置此消彼长：**越早越快，越晚知道得越多**。

学习路线（= [README](README.md) 的"入门到精通"主线）：

```
00(本文,建立地图) → 01(原理:VM/verifier/CO-RE) → 06(动手跑三个例子)
  → 07(读懂 ruport-go 源码) → 04/05(map与挂载深入) → 02/03(Go加载端/bpf2go)
  → 08/10(排障与调试) → 09(版本兼容) → 11/12/13(内核侧进阶) → 精通
```
